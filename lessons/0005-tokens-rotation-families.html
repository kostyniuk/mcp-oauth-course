Lesson 0005 · OAuth for the AMFG connector

Tokens, rotation and families

One Allow click becomes a family of rows. Use a dead one twice, and the whole family dies.

After 15 minutes you can read an oauth_tokens row, explain why we store only hashes, walk through a refresh and a replay, and defend "why not JWTs?"

What Claude gets back

POST /oauth/token   (application/x-www-form-urlencoded)
grant_type=authorization_code&code=…&code_verifier=…&redirect_uri=…&client_id=…&resource=…

200 OK   Cache-Control: no-store
{ "access_token": "3f9c…", "token_type": "Bearer", "expires_in": 3600,
  "refresh_token": "a71e…", "scope": "mcp:read mcp:write offline_access" }
Authorization code
5 minutes, single use. Fixed.
Access token
1 hour. Sent on every /mcp call. Configurable: MCP_OAUTH_ACCESS_TOKEN_LIFETIME_S.
Refresh token
30 days. Only ever sent to /token. Configurable: MCP_OAUTH_REFRESH_TOKEN_LIFETIME_S.

The short access token limits the damage if one leaks. The refresh token means the user doesn't have to click Allow every hour. It's issued because Claude asks for the offline_access scope.

Opaque, and stored only as a hash

Our tokens are opaque: 256 random bits as hex, with no meaning inside. The database never sees the token itself, only its SHA-256 hash. When Claude calls /mcp, we hash the bearer value and look for a row that is the right type, not revoked and not expired.

Passwords need a salt and a slow hash because people pick guessable ones. A 256-bit random token can't be guessed, so a plain SHA-256 is safe, and it lets us find the row by value in one indexed lookup.

A database dump or a stray log of the table gives an attacker nothing usable: you can't send a hash as a bearer token, and you can't reverse it.

The table

The oauth_tokens table has one row per code, access token or refresh token:

typeAUTHORIZATION_CODE, ACCESS_TOKEN or REFRESH_TOKEN

Families: one Allow, one grant

When /approve creates the code, it also creates a new family_id. Every token that grows from that code carries the same id. That family is the grant.

Rotation and replay

Each refresh returns a new refresh token and revokes the old one (RFC 9700 §4.14.2). A legitimate client always holds just the latest one. So if a revoked code or refresh token ever comes back, two parties have a copy, and we can't tell which is the thief.

The model's answer is revokeReplayedGrant: revoke the whole family and return invalid_grant. That's why used rows are kept with revoked_at rather than deleted. Deleting them would make a replay look like an unknown token, and nothing else would be revoked.

The same applies to codes: a code redeemed twice revokes the tokens the first redemption issued (test: "Should revoke the tokens of a code that is redeemed again").

The cost: a buggy client that retries a refresh with the old token disconnects itself. That's the trade the spec recommends. It doesn't happen in normal Claude use, and the fix is just to reconnect.

Ending a grant

  • Revocation: POST /oauth/revoke with any access or refresh token from the family revokes the whole family. It always answers 200 {}, even for unknown tokens (RFC 7009 §2.2), so it can't be used to probe which tokens exist. This is how a client ends its grant for good on our side.
  • Cleanup: the hourly OAuthTokenCleanup job deletes a family only when its newest expires_at is over a day old. It deletes whole families, never single rows, so a replay is still detected right up until the grant is gone.

Why not JWTs?

A JWT access token carries its claims and a signature, so an API can check it without a database. The catch is that it stays valid until it expires: revoking it means building a blocklist, which is a database lookup again.

We have one service that both issues and checks tokens. The lookup is one indexed read per /mcp call, and it buys instant revocation: revocation and replay detection take effect on the very next call (test: "Should reject an access token after its grant is revoked").

Defend it. A reviewer asks: "Why keep used and rotated-out tokens in the table? Just delete them."
They're our replay detector. A legitimate client never reuses a code or an old refresh token, so seeing one come back means a copy was stolen, and we revoke the whole family. If we deleted the row, the replay would look like an unknown token and the thief's copy (if used first) would keep its grant. The rows hold only hashes, and the hourly cleanup removes the whole family a day after its last token expires.
