Lesson 0006 · OAuth for the AMFG connector

Scopes, read-only and step-up

What a token may do, how a tool says what it needs, and who Claude acts as inside AMFG.

After 12 minutes you can say which scope each tool needs and why write tools need both, tell a 401 from a 403, walk through a step-up, and defend the app-scoped identity, including its weak spot.

Three scopes

mcp:read
Call the read tools. Consent label: "View tickets, parts and quotes".
mcp:write
Call the tools that create or change things. Consent label: "Create and change tickets, parts and quotes, including sending quotes".
offline_access
Not a permission on data: it asks for a refresh token (lesson 0005).

A scope is decided once, at consent, and written on every row of the grant. What ends up in the token:

  1. Start from what Claude asked for, minus anything we don't support. If Claude asked for nothing, start from all three.
  2. If the user ticked Read-only access, remove mcp:write.
  3. If no data scope is left (neither read nor write), refuse with invalid_scope. A token that can't call any tool is pointless.

Which tool needs what

Each MCP tool already declares readOnlyHint in its annotations. We derive the required scope from that, so there's no second list to keep in sync:

ToolsreadOnlyHintRequired
get_ticket, get_part, get_quotetruemcp:read
create_ticket, update_ticket, create_part, update_part, create_quote, update_quotefalsemcp:read + mcp:write

Why do write tools demand read as well? When a read-only token hits a write tool, the server tells Claude which scopes to ask for, and Claude gets a new token that replaces the old one. If the challenge said only mcp:write, the new token could create tickets but no longer read them. Asking for both keeps the replacement a superset.

401 or 403?

These two answers mean different things, and Claude reacts to each differently (401 vs 403, RFC 6750 §3.1):

SituationResponseClaude does
No token401, resource_metadata=…Discovery and sign-in (lesson 0003)
Expired, revoked or unknown token401, error="invalid_token"Refresh, or sign in again
Valid read-only token on a write tool403, error="insufficient_scope"Step-up: ask the user for more
HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope", scope="mcp:read mcp:write",
                  resource_metadata="https://dev.example.com/engine-service/public-api/v1/oauth/protected-resource"

The check runs before the tool body, so nothing is created (test: "Should ask a read-only token to step up before a write tool runs" checks that the downstream ticketCreate is never called). The MCP SDK's requireScopes does this, and we register it on every tool as scopeChallenge.

The MCP spec lets the client react to insufficient_scope by starting a new authorization for the listed scopes. The user then sees the consent screen again, this time without having ticked Read-only.

Who does Claude act as?

Once a token is accepted, the request runs exactly like one carrying an Incoming Secret:

store.tokenData = { userId: -1, appId: token.appId }   // what every downstream service sees
req.auth.extra  = { userId: token.userId }              // the real user, kept for the MCP layer

That's the app-scoped identity. The tools were built and tested against the Incoming Secret identity, so management-service, the sandbox methods and the existing permission checks see nothing new (test: "Should run tools with the App identity like an Incoming Secret"). Acting as the individual user would change what every tool may see. That's a separate decision, and the stored user_id keeps the door open for it.

The weak spot to name yourself in a review: any user who can sign in to an app can give Claude app-level reach. Today the gates are the consent screen, read-only, revocation, and only real users being able to approve. A per-user identity would be the follow-up if that isn't enough.

Who can approve: /approve accepts only a signed-in AMFG user, never an internal service call, a URL-prefix token or an app-scoped -1 caller (tests: "Should require a signed-in AMFG user to approve", "…platform token that names no user").

Where tokens work: only on /mcp. The REST routes under /public-api/v1 still require an Incoming Secret (test: "Should not accept an access token on the REST routes"). That keeps the new credential's reach as small as the feature needs.

Defend it. A reviewer asks: "So Claude runs as the whole app, not as the user who connected it? Isn't that too broad?"
Yes, deliberately for now. It's exactly how Incoming Secrets already run, so the nine tools behave as they were built and tested, and no downstream permission logic changes. The reach is bounded: a real signed-in user must approve, they can choose read-only, write tools need mcp:write, tokens work only on /mcp, and a grant can be revoked at once. We store the real user on every token, so moving to per-user identity later is a contained change.
