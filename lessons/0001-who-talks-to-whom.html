Lesson 0001 · OAuth for the AMFG connector

Who talks to whom

Four roles, two channels, and why Claude gets a code before it gets a token.

After 10 minutes you can name the four OAuth roles in our system, and answer the review question "why doesn't Claude just take the token from the consent page?" in two sentences.

The four roles

OAuth always has the same four parties (RFC 6749 §1.1). Once you can point at each one in AMFG, the rest of the protocol is just messages between them.

Resource owner
The AMFG user who clicks Allow. Their data is what's being shared.
Client
Claude (claude.ai or Claude Code). It wants to act for the user.
Authorization server
engine-service under /public-api/v1/oauth. It checks who's asking and hands out codes and tokens.
Resource server
engine-service's /mcp. It accepts tokens and runs the tools.

The spec explicitly allows the authorization server and the resource server to be the same server (§1.1). That's our choice: both live in engine-service.

The Management Console is not a fifth role. It's the authorization server's login and consent screen, borrowed so users sign in the way they always do.

Two channels

Messages travel two ways, and that difference explains most of OAuth's design.

The front channel is a browser redirect. Anything in it can end up in browser history, proxy logs, or an extension's view of the URL. So OAuth only lets a code travel there: it is single-use and short-lived (RFC 6749 §4.1.2 suggests 10 minutes at most; ours is 5).

The back channel is Claude calling engine-service directly over HTTPS. Only there does the code get swapped for real tokens (Parecki, "Web server apps").

A stolen code is still useless on its own. Lesson 0002 shows the extra lock, PKCE, that makes sure only the Claude that started the flow can redeem it.

Defend it. A reviewer asks: "Why can't Claude just read the token off the consent page?" Answer in two sentences, then compare.
The consent page lives in the browser, which is the front channel. URLs there can leak through history, logs or extensions, so it only carries a 5-minute, single-use code. Claude swaps that code for tokens on a direct HTTPS call to /oauth/token, and with PKCE (next lesson) only the Claude that started the flow can do that swap.
