Lesson 0007 · OAuth for the AMFG connector

Routing it to engine-service

Three exact paths at the host root, a one-line rewrite inside the app, and a template version that decides whether prod can ship.

After 10 minutes you can trace https://dev.example.com/mcp from the internet to the MCP route, explain why the rewrite lives in engine-service rather than the ingress, and list what's still between us and prod.

The problem

On every AMFG host, the root belongs to the Management Console. engine-service only answers under /engine-service/…. But lesson 0003 showed three URLs that must answer at the root:

https://dev.example.com/mcp
https://dev.example.com/.well-known/oauth-authorization-server
https://dev.example.com/.well-known/oauth-protected-resource/mcp

Everything else (/authorize, /token, /revoke, the consent API) stays on the existing /engine-service/public-api/v1/oauth/* route, because the metadata simply points there.

The path of one request

Step 1: the ingress, with Exact rules

The infrastructure config adds three extraIngressRules to engine-service's Ingress:

"extraIngressRules": [
  { "host": "dev.example.com", "path": "/mcp", "pathType": "Exact" },
  { "host": "dev.example.com", "path": "/.well-known/oauth-authorization-server", "pathType": "Exact" },
  { "host": "dev.example.com", "path": "/.well-known/oauth-protected-resource/mcp", "pathType": "Exact" }
]

Exact means precisely that path and nothing below it. A Prefix rule on /.well-known would steal every other well-known file from the Management Console, and /mcp as a prefix would also catch /mcp-anything.

Step 2: why the rewrite is in the app

The ingress forwards /mcp exactly as it arrived. It can't rewrite just these three paths: ingress-nginx's rewrite-target is an annotation on the whole Ingress, so it would also rewrite every normal /engine-service/… request. deployment-template's own comment warns that extra rules "only work unmodified".

So engine-service takes over, in root-paths.js. A tiny Express middleware, registered before any router, swaps req.url for the three known paths and keeps the query string:

const ROOT_PATHS = {
  '/mcp':                                     '/public-api/v1/mcp',
  '/.well-known/oauth-authorization-server':  '/public-api/v1/oauth/authorization-server',
  '/.well-known/oauth-protected-resource/mcp':'/public-api/v1/oauth/protected-resource'
};   // each target is also prefixed with API_PREFIX (/engine-service)

Tests call both URLs and expect identical results: "Should serve the MCP endpoint at the root path" and "…at the root well-known path".

The version gotcha

extraIngressRules first appears in deployment template 4.0.8. Older versions don't fail on the key. They silently ignore it: no error, no route, and /mcp lands on the Management Console.

Local (amfg-compose)n/a: nginx location = blocksYes
the dev environment^4.0.9Yes, verified end to end

If /.well-known/oauth-authorization-server on a host returns the Management Console's HTML instead of JSON, check the deployment template version first.

What's still between us and prod

  1. Template bump: bump prod to deployment template 4.0.8+ so the already-merged Exact rules take effect.
  2. Release port: all the changes (engine-service, Management Console consent page, infrastructure, compose) go into the next release.
  3. MCP_OAUTH_ISSUER set on prod to https://console.amfg.ai. Until then the feature is fully off (lesson 0003), so shipping the code early is safe.
  4. Directory listing: the business checklist for listing the connector in Claude's directory.

Practice

Order the hops of POST https://dev.example.com/mcp.
ingress-nginx matches the Exact /mcp rule
The request reaches the engine-service pod with path /mcp
rewriteRootPaths sets req.url to /engine-service/public-api/v1/mcp
The public API auth middleware checks the bearer token
McpRoute handles the JSON-RPC call
Why not let the ingress rewrite /mcp to /engine-service/public-api/v1/mcp?
Why pathType: Exact instead of Prefix?
Someone merges the prod Exact rules but forgets the deployment template bump. What happens?
Defend it. A reviewer asks: "Rewriting req.url inside the app feels hacky. Why not route it properly?"
The proper ingress rewrite isn't available: deployment template sets rewrite-target per Ingress, so it would rewrite every engine-service path, and a hand-written Ingress outside the template would drift. The ingress therefore only picks the service with three Exact rules, and a 20-line middleware maps those three exact paths to routes that already exist. It runs before routing, has no other effect, and is covered by tests that call both URLs.
