Lesson 0002 · OAuth for the AMFG connector

PKCE: the lock on the code

A stolen code is worthless if redeeming it needs a secret that never went through the browser.

After 12 minutes you can describe the attack PKCE stops, explain why the challenge can be public while the verifier can't, and answer "the code already lives 5 minutes and works once, so why add PKCE?"

The gap lesson 1 left open

A classic web app proves who it is at /token with a client secret, a password only its server knows. Then a stolen code is useless without that secret too.

Claude can't do this. Claude Code runs on your laptop, where anyone can read its files. claude.ai uses a published client id and no secret. Both are public clients: their metadata says token_endpoint_auth_method: "none". Without something extra, whoever holds the code can redeem it.

The attack: code interception

The code travels on the front channel, so it can end up in browser history, a proxy log, a browser extension, or a hostile process listening on the loopback port Claude Code uses. That is code interception (RFC 7636 §1):

  1. The user clicks Allow. engine-service redirects to http://localhost:53682/callback?code=AbC….
  2. An attacker reads that URL and posts the code to /oauth/token before Claude does.
  3. Without PKCE, the attacker gets an access token for the user's AMFG app.

"Single-use, 5 minutes" doesn't help here: the attacker only needs to use it first, which takes milliseconds.

The fix: commit to a secret, reveal it later

Before opening the browser, Claude makes a random code verifier (43–128 characters) and keeps it in memory. It sends only the challenge, the verifier's SHA-256 hash:

code_challenge = BASE64URL( SHA256( code_verifier ) )

This works because a hash is one-way. Publishing the challenge commits Claude to the verifier without revealing it.

Try it: this is exactly what Claude computes.

The default verifier is the example from RFC 7636 Appendix B; the challenge should read E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM. Change one character and it changes completely.

Why only S256

RFC 7636 also defines a plain method, where the challenge is the verifier. Anyone who saw the /authorize URL then knows the verifier, so the protection is gone. RFC 9700 §2.1.1 recommends S256, and the MCP spec requires it. Our metadata advertises code_challenge_methods_supported: ["S256"], and anything else is refused.

Where the challenge travels in AMFG

1
GET /oauth/authorize refuses a missing challenge or a method other than S256. It redirects back to Claude with error=invalid_request.
2
The challenge is packed into the signed authorization request that goes to the Management Console. The console can show the request but can't swap the challenge, because the signature would break.
3
POST /oauth/approve creates the code. saveAuthorizationCode checks for S256 again, because the library would happily issue a code without PKCE. The challenge is stored in the code's metadata column.
4
POST /oauth/token: the library hashes code_verifier and compares it with the stored challenge. A wrong verifier gives invalid_grant and consumes the code, so a guesser gets exactly one try (test: "Should consume the code on a wrong PKCE verifier").

The verifier itself is never stored. It arrives once at /token, is hashed and compared, and is discarded.

A bonus: it also stops code injection

Code injection runs the other way: the attacker pushes their stolen code into the victim's callback, hoping the victim's Claude redeems it and works on the wrong account. The victim's Claude sends its own verifier, which doesn't match the challenge stored with that code, so it fails (RFC 9700 §4.5). state covers a similar forged-response case, and we require it too.

One line for a review: the challenge is a public commitment, the verifier is the private proof, and the proof only ever travels on the back channel.

Defend it. A reviewer asks: "Claude has no client secret. What stops someone who steals the code from getting a token?" Answer in two sentences, then compare.
PKCE: Claude sends only a SHA-256 challenge through the browser and reveals the matching verifier only on its direct call to /oauth/token, where we check it, and we accept only S256. Someone with the stolen code doesn't have the verifier, a wrong guess burns the code, and the verifier is never stored or sent through the browser.
