Lesson 0003 · OAuth for the AMFG connector

Discovery and the resource

The user pastes one URL. Three hops later, Claude knows where to sign in, how, and what the token is for.

After 12 minutes you can trace the three discovery hops from https://dev.example.com/mcp, say why the metadata must sit at the host root, and explain what the resource parameter protects against.

One URL in, everything else discovered

When you add a connector in claude.ai, you type https://dev.example.com/mcp and nothing else. No client id, no login URL, no token URL. Claude has to find out:

  • Does this server want OAuth at all, and who is its authorization server?
  • Where are /authorize and /token?
  • Does it support PKCE S256 and CIMD client ids?

The MCP spec answers this with two standard documents under /.well-known/, chained like this (MCP: authorization server discovery):

Hop 1: the 401 points the way

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://dev.example.com/engine-service/public-api/v1/oauth/protected-resource", scope="mcp:read mcp:write"

That's the WWW-Authenticate header from RFC 9728 §5.1. If Claude sent a token we didn't accept (expired, revoked, made up), the header also carries error="invalid_token", so Claude knows to refresh or sign in again.

With MCP_OAUTH_ISSUER unset, the 401 has no header at all and every /oauth route returns 404. The feature is fully off; only Incoming Secrets work.

Hop 2: "I am this resource, ask that server"

The protected resource metadata is the API describing itself:

{
  "resource": "https://dev.example.com/mcp",
  "authorization_servers": ["https://dev.example.com"],
  "scopes_supported": ["mcp:read", "mcp:write"],
  "bearer_methods_supported": ["header"],
  "resource_name": "AMFG"
}

If a client skips the header, RFC 9728 §3.1 tells it to try the well-known path built from the resource URL: /.well-known/oauth-protected-resource/mcp. We serve the same document there too.

Hop 3: the authorization server's menu

From the issuer https://dev.example.com, RFC 8414 §3 builds https://dev.example.com/.well-known/oauth-authorization-server:

{
  "issuer": "https://dev.example.com",
  "authorization_endpoint": "https://dev.example.com/engine-service/public-api/v1/oauth/authorize",
  "token_endpoint": "…/oauth/token",
  "revocation_endpoint": "…/oauth/revoke",
  "code_challenge_methods_supported": ["S256"],
  "token_endpoint_auth_methods_supported": ["none"],
  "client_id_metadata_document_supported": true,
  "authorization_response_iss_parameter_supported": true,
  "scopes_supported": ["mcp:read", "mcp:write", "offline_access"]
}

Two rules make this document live at the host root, not under /engine-service/…:

  1. The well-known path is derived from the issuer, and our issuer is the bare host.
  2. The issuer inside the document must be identical to the one used to build the URL, or the client must reject it (§3.3). That stops one server from impersonating another's metadata.

The endpoints listed can be anywhere, so /authorize and /token stay on the existing /engine-service/public-api/v1 route. Only three exact root paths are new (lesson 0007 covers how they're routed).

The resource: whose token is this?

A bearer token works for whoever holds it. If an API accepted any token from any authorization server, a token minted for some other MCP server could be replayed at ours, and the reverse. Resource indicators (RFC 8707) bind every token to one API:

  • Claude sends resource=https://dev.example.com/mcp to both /authorize and /token, as the MCP spec requires.
  • We compare it in canonical form (origin + path, trailing slash ignored). Anything else gets error=invalid_target (test: "Should refuse a token request for a foreign resource").
  • The resource is stored on every token row, and /mcp checks it again on every call.

Today our authorization server only issues tokens for one resource, so the /mcp check is defence in depth. It becomes essential the day a second API trusts the same server.

The MCP spec forbids token passthrough: an MCP server must never accept tokens that weren't issued for it, and never forward its own tokens to other APIs (MCP security considerations). The stored and checked resource is how we keep the first half of that rule.

Defend it. A reviewer asks: "Why do we need three new root URLs instead of keeping everything under /engine-service?"
Users paste the clean https://…/mcp, and MCP clients discover everything from it. RFC 9728 and RFC 8414 put both metadata documents at fixed well-known paths derived from that URL and from the issuer (the bare host), and the issuer must match exactly. So /mcp and the two well-known documents must answer at the root. The real endpoints (/authorize, /token, /revoke) stay under the existing prefix, because the metadata simply lists them.
